# Agent Note: 会话取消归档与「归档」区

Status: implemented

[English](2026-08-21-workspace-session-unarchive.md) | 中文

## 问题

在 UI 中，归档一个会话曾是单行道。注册表保留会话日志与其 workspace 记账席位，但没有任何界面列出已归档会话，也没有控件撤销归档——一次误点就会把一段对话永久藏起来（文档记载的恢复方式是停掉 harness 后手改 `~/.dsh/storages/workspace.json`）。[会话归档 note](2026-07-31-session-archive-global-set.zh.md) 早已预留了反向操作——「未来取消归档时可恢复原位置」——但下游什么都没有落地。

## 决策

`unarchiveSession` 现在贯穿完整 seam，在每个角色上与 `archiveSession` 成对：注册表服务按既有归档顺序持久移除单个 id；`workspace.unarchiveSession` 应答与 changed frame 相同的完整集合快照；client manager/service 安装该回声而不等待 frame。

两个方向的幂等性不对称是刻意的，源自各自写入所授权的内容。归档校验存在性，因为它在铸造成员资格；取消归档只是溶解成员资格，所以什么都不校验——未知或已恢复的 id 直接完成且不写入，该 RPC 也没有业务失败分支。这也让 stray id 始终可移除：日志消失后 id 可能仍留在集合里，而对 stray 唯一合理的动作就是移除。

侧边栏浏览器在分组与平铺两种模式下各长出一个尾部的**「归档」区**，仅在集合非空时出现。它按最近更新优先列出已归档会话及其相对时间和实时状态，位于拖拽/排序机制之外——恢复（而非重排）是该区唯一的动词。空白占位行保持排除：新会话总是铸造全新 blank、绝不复用已归档 blank，因此已归档 blank 没有可恢复的目标。

点击已归档行会先取消归档再打开。运行时的清扫规则会清除任何仍落在归档集合内的当前选择（本地回声、他端 frame、重连基线共用同一条规则），所以在回声落地前打开会把刚恢复的会话直接打回新会话视图。把恢复并入打开手势保住了「打开中的会话必须始终可见」这一不变量；行菜单的「取消归档」则只恢复而不切换选择，服务于整理而非阅读的用户。

## 已考虑的替代方案

**视图选项里的开关（“显示已归档”），把归档行叠回正常列表。** 归档行会重新进入拖拽/排序账户和搜索，迫使每个派生函数和排序存储都推理两套可见性状态。独立的分区让现有派生保持不动：「归档即处处排除」仍是唯一规则，分区自行派生其行。

**打开即恢复但不取消归档。** 让已归档会话成为当前选择会与清扫规则正面冲突——投影会立即将其清除。放宽清扫以容纳“打开但隐藏”的状态则会破坏它真正的保证（隐藏行不得留在列表背后继续打开）。

**设置页里的归档管理器。** 归档/取消归档是贴着对话本身的逐会话手势；分离的页面只增加导航而不增加能力。

## 后果

取消归档在保留的记账席位上原位恢复会话，长期维护的手动顺序得以穿越归档往返。RPC 面新增一个方法；wire schema、carrier 表、fixture host、测试替身与生成目录都携带新成员，因为它们与方法映射是编译或新鲜度耦合的。搜索仍不匹配已归档会话；该区是其唯一出现之处。

## 测试

注册表单测覆盖有序移除、对未归档与未知 id 的幂等无操作、跨重启持久性以及记账不受影响。网关测试覆盖往返链路，包括每次提交恰好一帧快照。运行时测试覆盖 unary 回声安装与失败上抛。组件测试覆盖两种模式下的分区渲染、“先恢复后打开”的顺序、不开会话的菜单取消归档以及拒绝日志；tree 测试钉住派生的最近更新排序与排除项。`apps/web/tests/workspace-management.e2e.ts` 在真实 wire 上驱动 归档 → 重载 → 取消归档 全程。
